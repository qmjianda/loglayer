## Context

### 背景

LogLayer 当前依赖用户手动配置时间范围图层、过滤规则和高亮。用户需要更智能的方式来分析日志：
1. 时间戳格式多样（ISO8601、Unix 时间戳、自定义格式），用户难以手动配置
2. 大型日志文件中，用户需要反复尝试才能找到感兴趣的时间段
3. 复杂的日志模式难以用简单规则描述

### 现有约束

- **隐私优先**：AI 仅分析用户明确提供的内容（选中文本、聊天输入），不自动扫描整个文件
- **离线可用**：无 AI 时软件所有功能正常工作，AI 是增强而非必需
- **用户控制**：用户选择本地或云端 AI，自行管理 API Key

## Goals / Non-Goals

### Goals

1. **AI 助手聊天**：用户可以粘贴日志或选中日志片段，发送至 AI 分析
2. **时间戳智能检测**：分析日志样本，自动识别时间戳格式和正则表达式
3. **时间范围建议**：分析日志内容，推荐可能感兴趣的时间段
4. **灵活的 AI Provider**：支持本地 (Ollama)、云端 (OpenAI)、离线回退 (Heuristic)
5. **优雅降级**：无 AI 时提示用户配置，不阻塞正常功能

### Non-Goals

- **不分析整个文件**：仅处理用户明确提供的内容
- **不存储日志到云端**：所有处理在本地或用户可控的 API
- **不实现复杂 NLP**：聊天功能专注于日志分析场景，不做通用问答
- **不强制要求 AI**：基础功能完全独立于 AI

## Decisions

### D1: AI Provider 架构

**决策**：采用 Provider 抽象模式，支持可插拔的 AI 实现

```
┌─────────────────────────────────────────┐
│            AI Service (ai/service.py)    │
│         ┌─────────────────────────┐     │
│         │    Provider Interface    │     │
│         └─────────────────────────┘     │
│                  ▲                      │
│        ┌────────┼────────┐             │
│        │        │        │             │
│   ┌────┴───┐ ┌──┴──┐ ┌──┴──┐        │
│   │ Local │ │Cloud│ │Heur │        │
│   │(Ollama)│ │OpenAI│ │istic│        │
│   └────────┘ └─────┘ └─────┘        │
└─────────────────────────────────────────┘
```

**备选方案**：
- 直接集成 OpenAI → 不支持本地，限制用户
- 单一 AI 类 → 难以扩展新 Provider

**理由**：Provider 模式允许：
- 用户根据隐私/成本选择
- 离线时使用 Heuristic 回退
- 未来轻松添加 Claude、Gemini 等

### D2: API Key 存储

**决策**：使用 `keyring` 库存储 API Key，系统密钥链保护

**备选方案**：
- 明文存储 settings.json → 不安全
- 环境变量 → 不方便多模型切换
- base64 编码 → 伪安全

**理由**：`keyring` 调用系统密钥链（Windows Credential Manager / macOS Keychain / Linux Secret Service），安全且透明。

### D3: 聊天上下文管理

**决策**：会话级上下文，不持久化存储

```
User: [粘贴日志]        →  临时上下文
AI:  [分析结果]         
                         →  上下文丢弃
User: [新问题]          →  新临时上下文
```

**备选方案**：
- 持久化对话历史 → 隐私风险，存储膨胀
- 完全无上下文 → 无法追问

**理由**：
- 符合隐私优先原则
- 节省存储空间
- 日志分析通常是独立的片段查询

### D4: 时间戳检测策略

**决策**：采样分析（前 1000 行），使用 Heuristic + 可选 LLM

```
┌─────────────────────────────────────────┐
│        Timestamp Detection Flow          │
├─────────────────────────────────────────┤
│                                          │
│  User clicks "AI Detect"                │
│            │                            │
│            ▼                            │
│  ┌─────────────────────────┐            │
│  │ Sample first 1000 lines │            │
│  └────────────┬────────────┘            │
│               │                          │
│               ▼                          │
│  ┌─────────────────────────┐            │
│  │ Heuristic Pattern Match │──── OK ───▶│ Return format + pattern
│  └────────────┬────────────┘            │
│               │ No match                 │
│               ▼                          │
│  ┌─────────────────────────┐            │
│  │  LLM (if available)    │            │
│  └────────────┴────────────┘            │
│                                          │
└─────────────────────────────────────────┘
```

**备选方案**：
- 全文件扫描 → 慢，大文件不可行
- 仅 LLM → 依赖网络，本地体验差

**理由**：大多数日志格式是标准的，Heuristic 足以覆盖。LLM 作为增强，处理复杂格式。

### D5: 前端状态管理

**决策**：使用 React Context + useReducer 管理 AI 状态

```typescript
interface AIState {
  provider: 'local' | 'cloud' | 'heuristic';
  model: string;
  isConnected: boolean;
  chatHistory: ChatMessage[];
  isProcessing: boolean;
}
```

**备选方案**：
- Zustand → 引入新依赖
- Redux → 过度设计

**理由**：现有项目未使用状态管理库，Context 足以满足需求。

## Risks / Trade-offs

### R1: Ollama 本地模型性能

**风险**：本地模型可能运行缓慢或内存不足

**缓解**：
- 默认使用轻量模型 (llama3.2:1b, qwen2.5:0.5b)
- 显示加载状态和模型信息
- 允许用户切换到云端

### R2: API Key 安全

**风险**：API Key 可能被窃取或泄露

**缓解**：
- 使用系统密钥链存储，不存明文
- 设置面板显示/隐藏切换，不明文显示
- 提供测试连接功能验证有效性

### R3: 大文本处理

**风险**：用户粘贴超大日志导致内存问题或超时

**缓解**：
- 前端限制输入长度（100KB 软限制，500KB 硬限制）
- 后端流式处理，避免内存堆积
- 超过限制时提示用户精简

### R4: 网络依赖

**风险**：云端 AI 依赖网络，离线完全不可用

**缓解**：
- Heuristic Provider 作为离线回退
- UI 明确显示当前 Provider 和连接状态
- 无 AI 时显示友好提示，不阻塞功能

## Open Questions

1. **Q1**: 是否需要支持流式响应（streaming）？
   - 当前设计支持，但前端实现复杂度增加
   - 建议：MVP 先不支持，后续迭代

2. **Q2**: 如何处理多语言日志？
   - 当前假设中文/英文
   - 需要测试其他语言（日文、韩文等）时间戳格式

3. **Q3**: 是否需要预设 prompt？
   - 日志分析场景可以有系统 prompt
   - 建议：内置几个模板，用户可自定义

4. **Q4**: 错误处理策略？
   - API 超时、认证失败、模型不支持等
   - 建议：统一的错误提示，引导用户排查
