## Context

现状：一人公司模型（`docs/COMPANY_MODEL.md` + `.opencode/commands/company-*.md` + 4 个归档 specs）已有 grill-me 设计评审闸门、2 常设闸门、DoD、防呆规则，但缺反馈闭环——报告落盘后无提炼机制；评审无量化约束；产出物无第一性原理审视。动机参见 proposal.md - Why。

约束：
- 只改手册 + 命令 + 验收测试，不碰 AGENTS.md 与业务代码
- 命令是 markdown 编排指令（由主 Agent 解读执行），非代码——"实现"即修订指令文本
- 既有验收测试 `tests/unit/test_company_commands.py` 用关键词断言约束命令文件内容，新能力沿用该模式

## Goals / Non-Goals

**Goals:**
- 在命令文件中落地可执行的自学习闭环编排（复盘输入 → 待提炼可见 → 老板触发 → 立项落地）
- 强化 company-spec 的 grill-me 量化约束（≥3 轮诘问、含挑战隐含假设）
- 让 proposal 模板生成含「根本问题」小节
- 同步更新 COMPANY_MODEL.md 与 specs，保持三处一致（手册/命令/规范）

**Non-Goals:**
- 不实现任何代码/脚本（如自动扫描报告的脚本）——本变更只改编排指令，扫描行为由 company-report 命令指引主 Agent 执行
- 不改 AGENTS.md（老板 Gate 1 确认）
- 不做自动提炼（提炼由老板触发，本变更只建机制）

## Decisions

**D1: 复盘输入以「本次循环问题」小节嵌入现有报告，而非新建独立账本**
- 理由：零新增文件、报告已进 git 可追溯、不增加状态源（符合 COMPANY_MODEL.md 第 6 节"无额外状态文件，避免状态漂移"）
- 备选：独立 retro.md 账本——多一个状态源，需维护同步，否决

**D2: 提炼触发为老板显式触发，代理不自动执行**
- 理由：与老板决策边界一致；防止代理自改流程的失控风险
- 备选：定时/定量自动触发——流程改动属方向性决策，不应自动化，否决

**D3: 提炼结果落地走 /company-init 立项，而非代理直接改文件**
- 理由：符合 COMPANY_MODEL.md 第 7 节"本模型自身变更也走 OpenSpec 流程"
- 备选：代理直接改命令并汇报——绕过 Gate 1，违反 draft-only 精神，否决

**D4: 评审量化用"每产出物 ≥3 轮诘问 + ≥1 条挑战隐含假设"**
- 理由：可执行的量化下限，防止走过场；不扩闸门（保持 2 常设闸门），避免流程膨胀
- 备选：只加"挑战隐含假设"一条不加轮数——无量化约束，易流于形式；扩到 Gate 1/Gate 2——影响面过大，老板否决

**D5: 第一性原理以"proposal 含根本问题小节"落地，而非独立方法论章节**
- 理由：轻量、可验证（命令文件关键词 + proposal 模板说明），避免形式主义
- 备选：新增独立"第一性原理审查"闸门——重流程，老板否决

**D6: 验收测试沿用关键词断言模式（扩展 test_company_commands.py + 新增 test_company_self_learning.py）**
- 理由：与既有测试风格一致（先红后绿基线）；命令是 markdown，关键词断言可验证编排要素存在
- 备选：解析命令结构做行为测试——过度工程，命令由主 Agent 解读，无法精确模拟，否决

## Risks / Trade-offs

- [关键词断言脆弱（措辞微调即红）] → 断言用稳定的关键短语（如「本次循环问题」「待提炼问题」「3 轮」「挑战隐含假设」「根本问题」），实现时保持这些短语稳定
- [公司命令是"软编排"，主 Agent 解读质量不一] → 命令文本明确步骤与护栏，评审量化给出显式下限
- [自学习闭环实际依赖老板勤于触发] → company-report 显式展示「待提炼问题 N 条」作为提醒，把决策权留给老板但不隐藏
- [三处一致性（手册/命令/specs）漂移] → 本变更同步更新三处；归档时 specs 成为权威，手册/命令引用之
