# Proposal: fix-bookmark-filter-index

## Why

`logviewer-architecture-revamp` 之后，书签功能在"过滤视图"下出现行号语义错位：用户在过滤后的视图上添加书签时，记录的是**过滤后可见行的虚拟行号**；但点击书签跳转、书签预览、F2 最近书签跳转时，系统却把该编号当作**物理行号**解释，导致跳转到错误位置（跳到了"过滤前的行号"）。根源是重构只把写入端与渲染端更新为虚拟索引语义，消费端（跳转/预览/最近书签）仍残留 revamp 前的物理行号假设。无过滤时两套编号相等，问题被隐藏；一旦添加过滤图层立即暴露。

同时，过滤视图下 gutter 仅显示单一编号，用户无法同时得知"这行在原始文件中的位置"与"这是过滤结果的第几行"。

## What Changes

- **书签统一锚定物理行号**（原始文件行号）：gutter 点击添加书签、书签匹配判断、★ 星标渲染全部基于物理行号；跳转、预览、最近书签逻辑保持现有物理行号语义（本就正确，无需改动）。
- **行号侧边栏改为显示物理行号**：过滤视图下物理行号跳跃显示（如 10, 12, 14...），不再显示过滤序号。
- **新增虚拟行号列**：与物理列并排显示"过滤结果序号"（连续 1, 2, 3...）；物理列为主（正常亮度），虚拟列为辅（灰色、小字号）。
- **无过滤自动折叠虚拟列**：当可见行数 == 原始行数（无过滤）时虚拟列折叠隐藏，避免两列显示相同数字；折叠/展开带宽度过渡动画，gutter 宽度变化不产生内容区抖动。
- **新增设置项"显示虚拟行号"**：默认开启（仅过滤场景生效），可彻底关闭虚拟列。
- **位宽自适应**：物理列宽按原始行数位数自适应（下限 3 位），虚拟列宽按过滤后可见行数位数自适应（下限 2 位）。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `log-viewer-rendering`: 行号侧边栏（gutter）需求扩展为"物理 + 可折叠虚拟"双行号显示；书签标记需求明确书签数据锚定物理行号（过滤视图下仍精确命中原始行）。

## Impact

- **前端**：
  - `frontend/src/components/LogViewer.tsx`：gutter 点击传物理行号、书签判断改用物理行号、gutter 宽度动态化（物理 + 虚拟列宽）。
  - `frontend/src/components/logViewer/LogRow.tsx`：行号侧边栏渲染为物理列 + 虚拟列、★ 星标锚定物理列、按物理行号匹配书签。
  - `frontend/src/hooks/useSettings.ts` + `frontend/src/components/SettingsPanel.tsx`：新增"显示虚拟行号"设置项（默认开启）。
- **后端**：无行为修改（`toggle_bookmark` / `get_nearest_bookmark_index` / `get_lines_by_indices` 本就是物理行号语义），仅补充测试锁定语义。
- **测试**：`tests/unit/` 后端书签物理语义测试；`tests/e2e/` 过滤视图下书签跳转精确命中、双行号显示 / 折叠 / 设置开关。
- **已知遗留（非本次范围）**：bug 期间产生的旧书签为虚拟语义脏数据，不迁移、不清洗，由用户手动清除。

## Risks

- **bridgedLines 中行的字符串形态**：`LogRow` 收到的行数据存在纯字符串形态（无 `index` 物理行号字段），物理行号取不到时需退化显示虚拟行号兜底。
- **虚拟行号折叠判定信号**：以"可见行数 == 原始行数"判定无过滤，需覆盖 FILTER 图层与搜索 FILTER 模式，且不受 HIGHLIGHT / TRANSFORM / FOLDER 图层影响。
