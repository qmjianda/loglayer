# search-debounce Specification

## Purpose
定义搜索触发链路的去抖与竞态控制：所有搜索入口统一经单层防抖触发后端、维护请求序号使过期结果失效、支持取消挂起的在途请求，避免大文件上连续输入引发多次 ripgrep 扫描与过期结果覆盖。
## Requirements
### Requirement: 统一单层搜索防抖

系统 SHALL 对所有搜索入口（侧边栏 SearchPanel 与 Ctrl+F find widget）应用**单一统一防抖**（250ms）：用户连续输入仅在停止输入 250ms 后触发一次后端搜索；不得存在多重串联防抖导致两个入口延迟不一致或最坏延迟叠加。

#### Scenario: 连续输入只触发一次搜索

- **WHEN** 用户在 250ms 窗口内连续输入 "e"→"er"→"err"→"error"
- **THEN** 仅最后一次输入停止后触发一次后端搜索请求
- **AND** 中间态不触发后端 ripgrep 扫描

#### Scenario: 两个入口延迟一致

- **WHEN** 分别经侧边栏 SearchPanel 与 Ctrl+F find widget 输入相同搜索词
- **THEN** 两者到后端请求的防抖延迟一致（同为统一防抖层，无叠加）

#### Scenario: 输入间隔拉长逐次触发

- **WHEN** 两次输入间隔超过 250ms
- **THEN** 每次输入分别触发一次搜索（防抖不吞掉间隔足够长的独立输入）

### Requirement: 过期搜索结果失效

系统 SHALL 在搜索状态中维护单调递增的**请求序号**（每次触发搜索递增）与**已应用序号**（每次应用结果记录当前请求序号）；后端 `pipelineFinished` 等结果信号到达时，若请求序号等于已应用序号（该序号对应的结果已被应用，信号为迟到的残留/重复），则丢弃该信号，不得重复更新 UI 状态（匹配数、rank、加载态）。搜索进行中因新触发而废弃的旧结果，由既有后端 worker 取消机制（`_retire_worker`）与前端在途请求取消共同保证不再产生应用冲突。

#### Scenario: 新搜索结果正常应用

- **WHEN** 触发搜索 A 且其 pipelineFinished 信号到达
- **THEN** 结果被应用（匹配数/加载态更新）
- **AND** 已应用序号推进至 A 触发时的请求序号

#### Scenario: 已应用后残留信号被丢弃

- **WHEN** 搜索 A 的结果已应用后，A 的迟到/重复 pipelineFinished 再次到达（期间无新搜索触发）
- **THEN** 该信号被丢弃（请求序号 === 已应用序号）
- **AND** 不重复更新匹配数、不清除当前加载态

#### Scenario: 请求序号单调递增

- **WHEN** 连续触发搜索 A、B
- **THEN** B 触发后的请求序号大于 A 触发后的请求序号

### Requirement: 在途请求取消

系统 SHALL 支持取消挂起的在途搜索请求：统一防抖窗口内输入再次变化时，上一个挂起的请求被取消，仅发出最新请求；请求取消 SHALL 通过 AbortSignal 实现，且不得在取消路径抛未捕获异常。

#### Scenario: 防抖窗口内新输入取消旧请求

- **WHEN** 防抖定时器触发前用户再次修改搜索词
- **THEN** 上一个挂起的搜索请求被 abort
- **AND** 仅最新搜索词对应的请求被发出

#### Scenario: 取消不产生未捕获异常

- **WHEN** 请求被 abort（AbortError）
- **THEN** 不抛出未捕获异常，不影响后续搜索触发
