# COMPANY_MODEL.md — 一人公司开发模型运营手册

> 本手册定义 LogLayer 仓库的"一人公司"自主化开发模型：老板只做少量方向性决策，
> 监管/工作/回归/汇报等环节由子 Agent 按固定流水线自动完成。
> 配套编排命令见 `.opencode/commands/company-*.md`。

## 1. 角色结构（4+1）

| 角色 | 职责 | 落地方式 |
|:-----|:-----|:---------|
| **设计评审**（+1） | 在规格进入实现前做对抗式评审，识别方案漏洞、歧义、隐藏风险；**每产出物至少 3 轮诘问，其中至少 1 条为「挑战隐含假设」类问题**；不过闸不放行 | grill-me/grilling 技能 |
| **监管** | 拆解任务、调度工作、把关闸门、核对越界、遇到歧义升级给老板 | 主 Agent 执行 company-* 命令时兼任 |
| **工作** | 按 spec 写验收测试（红）→ 写实现（绿）；产出物与代码改动 | `task()` 调度 sisyphus / openspec-apply 技能 |
| **回归** | 跑验收测试 + 相关单测 + 静态门 + git diff 越界检查；UI 变更追加 e2e；生成汇报材料 | company-review 命令显式执行 |
| **汇报** | 每道闸门生成对话摘要 + 落盘报告（`docs/company-reports/`） | company-run/review 命令末段 |

流水线位置：

```
你（老板）── 2 常设闸门 + 紧急升级
        │
   [设计评审闸门] grill-me：spec 通过评审才放行实现
        │
     监管 ── 调度 ──> 工作（红→绿）
        │
     回归 ──> 汇报 ──> 你审批交付
```

## 2. 老板决策边界（2 常设闸门 + 紧急升级）

**老板保留的决策：**

| 闸门 | 时机 | 老板做什么 |
|:-----|:-----|:-----------|
| **Gate 1 立项** | 新变更开始前 | 批准"做什么"（`/company-init`） |
| **Gate 2 交付** | 回归通过、汇报就绪 | 审报告/PR，说"合并"或"打回"（draft-only，代理永不合并） |

**代理自决范围**（无需老板）：spec 细节措辞、测试写法、实现方式（spec 约束内）、内部重构、Bug 修复方案、工具选择（不新增依赖前提下）。`Fix:` 级小额 bug 修复（<2 小时）代理可自决并在汇报中事后告知。

**紧急升级（自动升级给老板，不等闸门）：**

- 回归中同一闸门**连续失败 3 次**（熔断，不再自动重试）
- **规格歧义**：多个合理解释且影响差异 ≥2 倍工作量
- **越界改动**：`git diff --name-only` 出现超出任务范围的文件

## 3. 完成定义（DoD）

一个变更在以下清单全部满足后才算完成、可进交付汇报：

- [ ] OpenSpec 产出物齐全（proposal / specs / design / tasks）
- [ ] 验收测试存在且**先红后绿**（有证据：红→绿）
- [ ] 相关验收测试 + 单测通过（`pytest`）
- [ ] 静态门干净：`npx tsc --noEmit`（前端改动）/ `ruff check backend tests`
- [ ] `openspec-cn validate` 通过
- [ ] 无遗留调试输出（符合仓库日志规范）
- [ ] UI/交互类变更：e2e 通过（`npm run e2e -- --light`）

> 本地回归只跑"相关测试 + 静态门"（快）；全量回归由 CI 承担（push/PR 自动跑
> pytest unit+integration + tsc + vitest + build），CI 红视为交付阻塞。

## 4. 防呆规则

| 规则 | 内容 | 防什么 |
|:-----|:-----|:-------|
| **draft-only** | 代理永不合并/推送；交付必须老板 Gate 2 点头 | 无界自主、越权合并 |
| **证据制** | 汇报必须附测试输出/diff 证据，禁止口头声称"全过" | 汇报注水、幻觉编辑 |
| **越界检查** | 回归时 `git diff --name-only` 与**所有活跃变更的 scope.md** 做归属并集判定：命中本变更放行；命中他变更标记为"其他变更工作"不升级；无归属才升级 | 无界自主、scope 蔓延、多变更并发误报 |
| **熔断** | 同一闸门连败 3 次停止自动重试并升级 | 级联失败、无限重试 |
| **卡壳即问** | 规格歧义/阻塞时暂停询问老板，不猜 | 猜测性实现、方向漂移 |

## 5. 开机仪式（老板日常最小操作）

```
1. /company-report          # 看今日状态：各变更进度 + 待你决策项（一屏摘要）
2. /company-init <描述>     # 要开新活：登记并批准立项（Gate 1）
3. /company-run <变更名>    # 驱动循环：评审→规格→红→实现→回归→汇报（全自动）
4. 审批交付（Gate 2）       # 审报告/PR → "合并" 或 "打回"
```

也可只跑部分阶段：`/company-spec <变更名>`（仅规格）、`/company-review <变更名>`（仅回归+汇报）。

## 6. 状态与账本

- **公司状态** = `openspec-cn list --json`（变更与任务进度，权威数据源）+ 每个变更的 `tasks.md` checkbox
- **文件归属** = 每个变更的 `openspec/changes/<变更名>/scope.md` 文件登记表（规格阶段生成，越界检查的归属判定依据；支持目录/通配模式）
- **公司史** = `docs/company-reports/<变更名>-<日期>.md`（每道闸门落盘，进 git 可追溯）
- 无额外状态文件，避免状态漂移

## 7. 试点与演进

- 首个试点：`engineering-foundation`（CI/lint 基建，纯流程无 UI）
- 跑顺后可按需把稳定环节固化为 agent 定义（当前为纯命令编排）
- 本模型自身变更也走 OpenSpec 流程（当前变更：`company-operating-model`、`refine-company-process`）

### 7.1 自学习闭环（复盘输入 → 待提炼 → 老板触发 → 立项落地）

流程不是静态手册，而是可进化的操作系统。每次循环沉淀问题，老板触发提炼，改进经立项后落地：

| 环节 | 机制 | 谁执行 |
|:-----|:-----|:-------|
| **复盘输入** | 每道闸门报告（`docs/company-reports/`）含「本次循环问题」小节，记录暴露的问题与改进建议；无则标注"无" | 汇报 |
| **待提炼可见** | `company-report` 汇总「待提炼问题 N 条」，列出来源报告 | 汇报 |
| **老板触发提炼** | 老板确认后，把问题组织为改进提案清单（问题 → 建议的防呆规则/命令修改）；代理不自动提炼 | 监管 |
| **立项落地** | 改进提案经 `/company-init` 批准立项后才修改流程文件；未立项前流程文件不被修改 | 老板 + 监管 |

**第一性原理要求**：产出物阶段 proposal 须包含「根本问题」小节（该变更解决的根本问题、约束、为何现在），并接受评审中对隐含假设的挑战——"因为旧流程这么做的"不是有效理由。
